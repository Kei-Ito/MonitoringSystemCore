# データ保存仕様 (Data Persistence)

本ドキュメントでは、`apps/backend/src/services/dataSaveService.ts` におけるセンサーデータのCSV保存処理の仕様と実装詳細について記述します。

## 1. 保存形式

センサーデータは日付ごとのディレクトリに分割されたCSVファイルとして保存されます。

- **保存パス**: `{DataRoot}/{YYYY}/{MM}/{DD}/data.csv`
  - `DataRoot`: システム設定 (`SystemSetting`) で指定されたルートディレクトリ
- **文字コード**: UTF-8 (BOM付き)
  - Excel等での直接閲覧を考慮し、BOM (`\uFEFF`) を付与しています。
- **ヘッダー構成 (3行)**:
  1. **チャンネル名**: ユーザーが識別する名称 (例: "温度センサ1")
  2. **単位**: データの単位 (例: "℃")
  3. **チャンネルUUID**: システム内部で一意に識別するID

### CSV構造例
```csv
HEADER,温度センサ1,圧力センサ1
HEADER,℃,Pa
HEADER,1001,1002
2023-10-27T10:00:00.000Z,25.4,1013
2023-10-27T10:00:01.000Z,25.5,1012
```

## 2. 保存プロセス (`saveInputDatas`)

データの保存は以下のフローで行われます。

1. **排他制御 (Lock)**
   - ファイル書き込みの競合を防ぐため、簡易的なMutex (`acquireLock` / `releaseLock`) を使用して処理を直列化します。

2. **パス生成**
   - データのタイムスタンプに基づき、保存先のディレクトリとファイルパスを決定します。ディレクトリが存在しない場合は自動生成します。

3. **ヘッダー整合性確認 (`ensureCsvHeader`)**
   - 保存しようとしているデータ（チャンネルUUID）が、既存のCSVファイルに含まれているかを確認します。
   - **最適化**: ファイルI/Oを削減するため、後述するキャッシュ機構を使用します。
   - 未登録のチャンネルがある場合、ファイル全体を読み込み、ヘッダーと既存行に空のカラムを追加してファイルを再構築 (`rewriteHeader`) します。

4. **データ追記**
   - 確定したヘッダーの順序に従ってデータを並べ替え、CSV行を生成してファイルの末尾に追記 (`fs.appendFile`) します。

## 3. パフォーマンス最適化 (Header Caching)

高頻度（例: 100ms周期）でのサンプリング時に、毎回ファイルを開いてヘッダーを確認するのはI/O負荷が高いため、インメモリキャッシュを導入しています。

### 仕組み
- **キャッシュ**: `headerCache` (`Map<string, string[]>`)
  - キー: CSVファイルの絶対パス
  - 値: そのファイルの現在のヘッダー（UUIDリスト）

### 動作フロー
1. 保存リクエストが来ると、まず `headerCache` を確認します。
2. **キャッシュヒット**:
   - キャッシュされたヘッダーに、今回保存する全てのチャンネルUUIDが含まれているか確認します。
   - 全て含まれていれば、**ファイル読み込みをスキップ**し、即座にデータ追記へ進みます。
3. **キャッシュミス (またはカラム不足)**:
   - ファイルの先頭3行を読み込みます（ファイルが存在しない場合は新規作成）。
   - ヘッダー情報を解析し、キャッシュを更新します。
   - 必要であればヘッダー書き換え (`rewriteHeader`) を行い、最新のヘッダー構成でキャッシュを更新します。

この仕組みにより、通常運用時（チャンネル構成が変わらない場合）は、ファイルオープンは「追記」の1回のみとなり、読み込みオーバーヘッドがゼロになります。

## 4. 読み込み処理

トレンドデータ表示などのためにデータを読み込む際は、`fs.createReadStream` と `csv-parser` を使用してストリーム処理を行い、メモリ使用量を抑制しています。
- **`readFirstNLines`**: ヘッダー確認用に先頭N行だけを効率的に読み込むユーティリティ。
- **`loadCsvColumn`**: 特定の列（チャンネル）のみを抽出して読み込む処理。
